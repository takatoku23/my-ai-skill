# レビューしやすいコミット

作業開始時に、変更を「何のために変えたか」で説明できる単位に分ける。
全変更を最後に一括コミットせず、意味のある区切りを検証して順に記録する。

- 依存の追加、動作の変更、機械的な移動、開発ツール設定、説明文の更新は、それぞれ独立して確認できるなら分ける。
- 実装とその動作を保証するテストは同じコミットに含める。ファイル数や行数で機械的に分割しない。
- 型契約と呼び出し側など、分けると壊れる変更は一緒にする。可能な限り各コミットで型検査・対象テストが通る状態にする。
- 純粋な移動と動作変更を分けられる場合は分け、読者が差分から変更理由を追えるようにする。
- lint導入で既存コードの修正が必要なら、ルールと最小限の対応をまとめ、常に失敗するチェックを途中に残さない。

ステージ前に差分と既存の作業を確認し、対象パスまたはhunkを明示して追加する。
コミット前にステージ済み差分を確認し、無関係な変更や生成物を巻き込まない。
メッセージはリポジトリの慣例に合わせ、変更対象と目的を具体的に書く。
小さく分けるために他者の変更をreset・stashしたり、未依頼の修正を加えたりしない。

## 指摘を反映するとき

PR のレビュー指摘や、AI の出力に対する利用者の指摘を反映するときは、最終的なコミット列を「最初から正しく書いた」形にする。「レビュー指摘を修正」「typo 修正」のような後追いのコミットを積まない。

1. 指摘ごとに、修正対象の行を入れたコミットを `git log -L` や `git blame <base>..HEAD` で特定する。
2. 修正をそのコミットごとに分けてステージし、`git commit --fixup=<sha>` で記録する。1 つの指摘が複数のコミットにまたがるなら、hunk 単位でステージして fixup も分ける。コミットメッセージを直すなら、エディタを開かずに済むよう `git commit --allow-empty -m "amend! <元の件名>" -m "<新しいメッセージ全体>"` で記録する（`--fixup=reword:` はエディタを開く）。
3. 指摘が既存のコミットのどれにも属さない新しい関心事（機能の追加、別の不具合の修正）なら、fixup にせず独立したコミットにして、コミット列の適切な位置へ置く。
4. 指摘をまとめて反映し終えたら、rebase 前の HEAD を記録してから畳む。base は変えない（base の更新は別の作業として扱う）。

   ```bash
   before="$(git rev-parse HEAD)"
   base="$(git merge-base HEAD origin/<default branch>)"
   GIT_SEQUENCE_EDITOR=: git rebase -i --autosquash "$base"
   git diff --exit-code "$before" HEAD   # 最終ツリーが変わっていないこと
   git range-diff "$base" @{u} HEAD        # push 済みの状態からどのコミットが変わったか
   ```

   conflict が出たら、解消した内容を利用者に示す。解消に判断が要るなら `git rebase --abort` で戻して相談する。
5. 書き換えたコミットごとに、型検査と対象テストが通ることを確認する。
6. push は `git push --force-with-lease` で行う。拒否されたら他者が push しているので、上書きせずに取り込み方を利用者と決める。
7. 指摘への返信には、どの指摘をどのコミットへ反映したかを書く。履歴を書き換えると GitHub の「前回のレビューからの変更」が追いにくくなるため、`range-diff` の要点を添える。

履歴を書き換えてよいのは、自分が作った未マージの PR branch で、ほかの人がその branch にコミットしていない場合に限る。repository の規約が force push を禁じている、squash merge しか使わない、または他者のコミットが混ざっている場合は、書き換えずに追加コミットで反映し、その理由を伝える。デフォルトブランチとマージ済みの branch は書き換えない。

push 前のローカルのコミットは、利用者の作業中の変更を巻き込まない範囲で、同じ手順でいつ整理してもよい。

このスキルはpush・公開・マージ・デプロイの権限を追加しない。現在の依頼で許可された範囲を守る。指摘の反映を頼まれた PR branch への `--force-with-lease` での push は、反映の依頼に含まれるものとして扱う。
